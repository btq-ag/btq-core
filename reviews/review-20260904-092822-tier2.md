# Tier 2 review — the largest new logic

Five scopes, reviewed individually and context-blind. #183 was reviewed as an
incremental diff on top of #181, which is how the stack actually merges.

Every finding was verified against the code before disposition. **One `high` was

## Findings by PR

### PR #194 — weight-based orphanage

**[high] The headline feature does not fire on ordinary INV relay.**
`src/net_processing.cpp:4205`. `AddAnnouncer()` is called only inside the `TX`
message handler, under `if (AlreadyHaveTx(GenTxid::Wtxid(wtxid)))`. In normal relay a
second peer announces by **INV**, the INV path sees `AlreadyHaveTx() == true`, sends no
`getdata`, and the peer never sends the transaction — so `AddAnnouncer` is never
reached. Verified: the only non-test call site is line 4205, and the INV handler drops
already-known announcements.

The result is that "fetch parents from every announcer" works only when a peer
unsolicitedly re-pushes the full transaction. A first announcer can still withhold
parents while later announcers are ignored — the exact failure issue #202 describes.

**[medium] Witness-malleated variants corrupt the txid index.**
`src/txorphanage.cpp:57`. `m_orphans` is keyed by wtxid, so two transactions with equal
txid and different witnesses both get stored. But `m_txid_to_wtxid.emplace(hash, wtxid)`
is a no-op when the key exists, so only the first mapping survives. The second variant
becomes invisible to txid lookups, and erasing the first removes the only txid mapping.
`ProcessOrphanTx()` erases by txid, so it removes an arbitrary variant or none.

**[medium] Announcer bookkeeping escapes the accounting it is bounded by.**
`GetUsage()` returns only `GetTransactionWeight`, so announcer sets are not charged to
`m_total_orphan_usage`, and `NeedsTrim()` never sees them. `AddAnnouncer` does not
trigger `LimitOrphans()`. The latency cap does bound orphan count at ~3,000 and
connections at 125, so the exposure is bounded — roughly 375,000 set nodes, ~15 MB on
top of the 16 MB payload ceiling — but it is unaccounted and scales with
`-maxconnections`. Eviction of a widely-shared orphan is also about `O(P(P+3000))`.

**[low] Man pages still describe `-maxorphantx` as a count.** Runtime help and
`share/examples/btq.conf` were updated; `doc/man/btqd.1` and `doc/man/btq-qt.1` were not.

**[low] No regression test for the multi-announcer path.** The new test calls
`AddAnnouncer()` directly, so it passes despite the INV path never reaching it.

### PR #193 — fee estimator for 60-second blocks

**[medium] Two sufficiency thresholds were not scaled, making them 10x stricter.**
`src/policy/fees.h:180,182`. `SUFFICIENT_FEETXS = 0.1` and `SUFFICIENT_TXS_SHORT = 0.5`
are per-**block** rates and were left unchanged while every decay was retuned by 10x.
The acceptance threshold is `sufficientTxVal / (1 - decay)`:

| Horizon | Before | After |
|---|---|---|
| Short | `0.5 / (1-0.962)` = 13.16 | `0.5 / (1-0.99616)` = **130.21** |
| Medium | `0.1 / 0.0048` = 20.83 | `0.1 / 0.00048` = **208.33** |
| Long | `0.1 / 0.00069` = 144.93 | `0.1 / 0.000069` = **1449.28** |

Same wall-clock history, ten times the required transaction count. One transaction per
50 minutes is 0.2 tx/block upstream (passes 0.1) but 0.02 tx/block here (fails).
Verified both constants unchanged in the diff.

**[medium] The short horizon scales a different dimension than its siblings.**
`src/policy/fees.h:154-161`. Short went `periods 12 -> 120` with `scale` still 1; medium
and long kept their period counts and multiplied `scale` by 10. All three products grow
10x, but short's bucket width drops from 10 wall-clock minutes to 1, giving it different
resolution and 10x the confirmation/failure arrays. `SHORT_BLOCK_PERIODS=12` with
`SHORT_SCALE=10` would match its siblings.

**[medium] Wallet and GUI fee targets are not wall-clock equivalent.**
`DEFAULT_TX_CONFIRM_TARGET` is still 6 (`src/wallet/wallet.h:131`) — one hour upstream,
**six minutes** here. The GUI list was transformed by inconsistent positional factors
(1, 1.5, 2, 2.5, 2.5, 3.75, 5, 2.857) and drops the week-long target. This changes
wallet fee policy, not just estimator history. Notably `src/rpc/fees.cpp:35` already
says "six minutes, not an hour" — the help acknowledges the shift the default does not.

**[low] Tests were weakened rather than retargeted.** Exact scale-aligned fee
expectations became `estimate > 0`, while the workload still adds four transactions per
block — ten times the prior wall-clock rate.

**[low] RPC help claims BIP141 virtual-size semantics.** `src/rpc/fees.cpp:35,109` say
vsize is "as defined in BIP 141", which divides weight by 4. BTQ divides by
`WITNESS_SCALE_FACTOR = 16`. A 4x discrepancy, most visible on witness-heavy Dilithium
transactions.

### PR #192 — CoinGrinder

**[medium] The iteration cap does not bound clone-skipping work.**
`src/wallet/coinselection.cpp:387`. `TOTAL_TRIES = 100,000` counts evaluated selections
via `curr_try`, but the inner `while` loop that skips equal-effective-value clones is not
charged against it, giving worst-case `O(TOTAL_TRIES x N)`. Verified the loop exists and
is uncounted. **This code matches upstream verbatim**, so it is an inherited
characteristic rather than a BTQ mistake — but a Dilithium wallet with a long run of
equal-value UTXOs is a more realistic trigger here, and transaction creation holds wallet
state while it runs.

**[medium] The test verifies almost nothing about the new algorithm.**
`src/wallet/test/coinselector_tests.cpp:190`. The `add_coin` helper sets
`input_bytes = -1`, so every `OutputGroup::m_weight` is zero — the weight-minimising
algorithm is tested with no weights. The assertions are the algorithm tag and
`selected_value >= 3*CENT`; an implementation that ignores the change target, picks a
non-minimal set, or mishandles max weight passes. Upstream's cases for insufficient
funds, max weight, mixed weights, clones and iteration exhaustion were not ported.

### PR #181 — refuse trivial P2MR leaves

**[high] The guard does not catch the class of leaf it claims to.**
`src/wallet/p2mr.cpp:341`:
```cpp
bool IsTrivialP2MRLeaf(const P2MRTreeLeaf& leaf)
{
    return leaf.script.empty() || IsOpTrueLeaf(leaf);
}
```
and `IsOpTrueLeaf` requires `script.size() == 1 && script[0] == OP_TRUE`. So it catches
an empty script and exactly `OP_TRUE` — and nothing else. It misses `OP_2`,
`OP_DROP OP_TRUE`, every `OP_SUCCESSx`, and all nonempty unknown-version leaves.

The repo's own test demonstrates the gap: `test/functional/feature_p2mr_rpc.py:104-106`
funds a `"7551"` (`OP_DROP OP_TRUE`) leaf via `sendtop2mr(...)` with **no**
`allow_trivial_leaves` argument. Verified. So the default path funds an
anyone-can-spend output while the guard reports it is preventing exactly that.

**[medium] The new default breaks the Qt OP_TRUE workflow with no way to opt in.**
`src/wallet/p2mr.h:151`. The boolean was added to `CreateP2MR`/`FundP2MR` but not
plumbed through `interfaces::Wallet::{createP2MR,fundP2MR}`, `WalletImpl`, or
`P2MRController`. The Qt dialog's advertised "OP_TRUE leaf (regtest only)" template
calls `wallet().createP2MR(...)` without it, so that template now always fails.

### PR #183 — P2MR dump and restore (stacked on #181)

Metadata loss here makes funds permanently unspendable, so these are weighted as
critical rather than medium.

**[critical] Truncated records are silently treated as a successful restore.**
`src/wallet/rpc/backup.cpp:612`. A line is recognised as P2MR only if it already has
three or more fields and valid hex. `p2mr`, `p2mr <time>`, or a truncated non-hex third
field falls through to the ordinary key parser and is **silently ignored**. There is no
`# End of dump` footer check and no expected P2MR record count. A truncated backup
imports every private key, reports success, and omits the Merkle trees needed to spend.

**[critical] Restore discards the commitments that would detect corruption.**
`src/wallet/rpc/p2mr.cpp:395`. `listp2mr` exports `address`, `scriptPubKey`,
`merkle_root` and `wallet_address`; `importp2mr` reads only `tree` and `label`. A
one-byte change to a leaf script stays valid hex, changes the Merkle root, and produces
a different address — import reports success and the restored metadata cannot spend the
original output.

**[high] `importp2mr` throws on every invocation.** `src/wallet/rpc/p2mr.cpp:364`
declares `tree` as `RPCArg::Type::ARR` through the four-argument overload, which asserts
`CHECK_NONFATAL(type != Type::ARR && ...)` at `src/rpc/util.h:224`. Independently found
and reported before this review; it is the cause of the PR's red CI.

**[high] Descriptor import never rescans.** `src/wallet/rpc/p2mr.cpp:397` stores the
destination and returns. A restored address shows no balance and `createp2mrspend`
cannot select the output — so the PR's own functional test could not pass even with the
RPCHelpMan bug fixed.

**[high] Legacy import discards the original creation time.**
`src/wallet/rpc/backup.cpp:752` uses the dumped timestamp for the current rescan but
persists `created_at = GetTime()`. A second dump/restore generation then starts its
rescan near `T_import - TIMESTAMP_WINDOW` and can miss older funding.

**[medium] No leaf-count or byte-size limits on import.** A valid depth-20 tree is
`2^20 = 1,048,576` leaves; branch hashes alone need `1,048,576 x 20 x 32` = 640 MiB
before scripts and JSON copies. The dump-file path has no RPC request-size limit.

**[medium] Duplicate-tree handling loses labels from ordinary P2MR backups.**
`src/wallet/rpc/backup.cpp:718`. Dilithium key import synthesises a single-leaf entry
with an empty label first; the later metadata record carries the real label but
`CreateP2MR` sees an identical tree and returns without updating it.

**[medium] Tests omit every case above.** The unit round trip uses `OP_TRUE`, checks
address and label, and never verifies a funded balance or a spend.

## Note on CI

Only `Build btqd and run address tests` runs on a PR (`ci.yml` disables macOS and Win64
with `if: false`). It does run `make check`, so unit-test compilation and unit-test
failures are caught — that is how #183's RPCHelpMan bug surfaced. Functional tests are
not run, which is why several findings above are invisible to CI.
