# Tier 1 review — consensus and policy defaults

Five PRs with small diffs and large blast radius, reviewed individually and
context-blind. Every finding below was independently verified against the code
before disposition; verification notes are recorded inline.

Reviewed against `.claude/code-review-lanes.md`, written for this run. No

## Findings

### [high] #189 — ungated clock switch can split patched and unpatched nodes mid-testnet
**Where:** `src/init.cpp:1450` (and every `NodeClock::now` site in the diff) · **Lane:** consensus divergence

Header acceptance changes from `H <= system_time + peer_offset + MAX_FUTURE_BLOCK_TIME`
to `H <= system_time + MAX_FUTURE_BLOCK_TIME`, with no activation height.

The reason this matters more in BTQ than upstream is a constant BTQ changed and
one it did not:

- `MAX_FUTURE_BLOCK_TIME` = `15 * 60` = **900 s** (`src/chain.h:24`) — reduced for 60-second blocks
- `DEFAULT_MAX_TIME_ADJUSTMENT` = `70 * 60` = **4200 s** (`src/timedata.h:16`) — inherited from Core unchanged

Upstream Core has adjustment 4200 < allowance 7200, so the clock switch narrows an
already-larger window. **BTQ has the relationship inverted: the peer adjustment window
is 4.7x larger than the future-block allowance.** An old node carrying a `+4200`
offset accepts headers up to `T+5100` that a patched node rejects until `T+3300` — a
~55-minute disagreement window, sustainable by a miner that maintains the offset.

`BLOCK_TIME_FUTURE` is not cached, so the disagreement is recoverable rather than a
permanent fork. It is still a live-testnet rollout hazard.

### [high] #184 — silently reverts a documented BTQ decision, on a rationale that does not hold
**Where:** `src/kernel/mempool_options.h:22` · **Lane:** backport fidelity, resource limits

Restoring Bitcoin Core's 300 MB literal undoes commit `9c97fc7ab`, whose message reads
*"increase DEFAULT_MAX_MEMPOOL_SIZE_MB from 300 MiB to 2 GiB to prevent pathological
eviction with PQ-sized transactions and packages."* #184 does not mention or rebut that
reasoning.

The PR's own stated rationale — *"Dilithium witnesses make a larger default worse (more
expensive-to-verify junk), not better"* — is incorrect: transactions are fully verified
**before** mempool size limiting, so lowering the retention cap does not avoid the
verification cost it cites.

Sizing, from the review: a minimal 1-in/1-out single-leaf P2MR Dilithium transaction is
~5,252 WU (~329 vB), so 300 MB retains roughly 42 blocks (~42 minutes at 60-second
spacing) versus ~282 blocks (~4.7 hours) at 2 GB. Once full, `TrimToSize()` raises the
rolling minimum fee, suppressing honest low-fee relay while it decays.

### [medium] #185 — the "mineable in one block" invariant the change is built on does not hold
**Where:** `src/policy/policy.h:67` · **Lane:** correctness, focus

The new limits equate package capacity with the full consensus block weight:
`500 kvB x 1,000 x 16 = 8,000,000 WU`. But `BlockAssembler` caps templates at
`DEFAULT_BLOCK_MAX_WEIGHT = 7,600,000` (`src/policy/policy.h:24`) and starts with
`nBlockWeight = 4000` reserved (`src/node/miner.cpp:98`), rejecting on
`nBlockWeight + WITNESS_SCALE_FACTOR * packageSize >= nBlockMaxWeight`
(`src/node/miner.cpp:204`).

Solving: `4000 + 16 * vsize < 7,600,000` gives **vsize <= 474,749 vB**. The change
permits ancestor sets up to 500,000 vB, so the top ~5% of the permitted range cannot be
mined in one template by this node — contradicting the comment added in the same diff.

Verified independently. All four `static_assert`s in `src/policy/packages.h` do hold
(the ancestor/descendant ones at exact equality), and the blocks-only floor correctly
lands on 20 MB.

### [medium] #188 — the new default breaks two functional tests the PR does not touch
**Where:** `src/kernel/mempool_options.h:30` · **Lane:** backport fidelity, tests

Both verified present and asserting the old behaviour:
- `test/functional/mempool_accept.py:154` expects `txn-mempool-conflict` for an
  opt-out replacement paying more fee — full-RBF now accepts it.
- `test/functional/p2p_permissions.py:122` expects `txn-mempool-conflict` — the tx now

Upstream updated both in the corresponding commit; this port did not. **No functional
tests run in this repo's CI**, so neither failure will surface on its own.

### [medium] #188 — nothing tests full-RBF as the *unset* default
**Where:** `test/functional/feature_rbf.py:36` · **Lane:** tests

The PR adds `-mempoolfullrbf=0` to **both** nodes, and `test_fullrbf()` restarts with
`-mempoolfullrbf=1`. Every mode the test exercises is now selected explicitly, so the
suite passes identically whether `DEFAULT_MEMPOOL_FULL_RBF` is `false` or `true` — the
one behaviour this PR exists to change is untested.

### [medium] #189 — no test distinguishes adjusted-time from system-time validation
**Where:** `src/test/util/setup_common.cpp:183` · **Lane:** tests

The test changes only swap fixture callbacks. No test sets a nonzero peer offset, so
existing future-time tests pass identically before and after. Nothing would catch a
missed call site or the 900/901-second boundary.

### [medium] #186 — the raise/keep guidance is self-contradictory
**Where:** `src/script/script.h:72` · **Lane:** correctness

"Keep 50 if `ceil(ratio * 1.5) <= 50`" means keep only when ratio <= 33.3. The next
line says raise only when the ratio is "well above 50." A measured ratio between ~33.4
and 50 satisfies neither rule — e.g. ratio 40 gives `ceil(60) > 50`, requiring a raise
the second sentence discourages.

Confirmed useful context from the same review: at `DILITHIUM_SIGOP_COST = 50` the sigop
budget allows `80,000 / 50 = 1,600` Dilithium inputs, versus ~1,817 by weight
(`8,000,000 / 4,402`). Sigops bind first, so the constant is doing real DoS work.

### [low] #189 — `-maxtimeadjustment` now advertises behaviour it no longer has

by this amount" — is now false. `ChainstateManager::Options::adjusted_time_callback` and
`chain.h` likewise still describe adjusted time, inviting a future caller to reintroduce
peer time into validation.

## Disposition

- [high] #189 ungated clock switch splits patched/unpatched nodes — **ACCEPTED.** Verified `MAX_FUTURE_BLOCK_TIME=900` vs `DEFAULT_MAX_TIME_ADJUSTMENT=4200`. Needs a coordinated testnet rollout, or reduce max adjustment to <= 900 s before switching. Does not block the change itself, which is a correct upstream backport.
- [high] #184 reverts a documented decision on a false rationale — **ACCEPTED.** Verified against commit `9c97fc7ab`. Recommend closing #184 unless a measured backlog target replaces the copied Core literal.
- [medium] #185 one-block mineability invariant violated — **ACCEPTED.** Verified: 474,749 vB template ceiling vs 500,000 vB policy limit. Fix is to use 474 kvB, or drop the mineability claim.
- [medium] #188 breaks `mempool_accept.py` and `p2p_permissions.py` — **ACCEPTED.** Both verified present and asserting the old behaviour.
- [medium] #188 new default untested — **ACCEPTED.** Verified: the PR pins the option off on both nodes.
- [medium] #189 no adjusted-vs-system-time regression test — **ACCEPTED.**
- [medium] #186 contradictory raise/keep thresholds — **ACCEPTED.** Verifiable from the diff text alone.
- [medium] #189 headerssync commitment bound can wrap — **PRE-EXISTING.** The same expression is on master with `GetAdjustedTime` (verified via `git show origin/master:src/headerssync.cpp`) and in upstream Core; `m_max_commitments` is `uint64_t`, so a negative numerator converts to a huge bound. Real, but not introduced here. File separately; do not fix inside #189.
- [low] #189 `-maxtimeadjustment` help is now false — **ACCEPTED.** Independently confirmed zero remaining `GetAdjustedTime` callers.
- [low] #188 manpages and `btq.conf` stale — **ACCEPTED.** All three verified.
- [low] #185 test pins nothing — **ACCEPTED.**
- [low] #186 "conservative" unmeasured — **ACCEPTED.** Benches confirmed pre-existing.
- [low] #184 no regression test — **ACCEPTED**, moot if #184 is closed.

### Declined
- #184 — hypothesis that the `* 40` literal in `DEFAULT_BLOCKSONLY_MAX_MEMPOOL_SIZE_MB` is a stale `WITNESS_SCALE_FACTOR` assumption: **DECLINED.** It is upstream's 40x descendant-set factor, predating SegWit. Independently confirmed; the reviewer reached the same conclusion unprompted. `2000 kvB * 1000 * 40 = 80 MB`, and the new 300 MB default clears it.
